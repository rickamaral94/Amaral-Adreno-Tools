Revisei o sparse2 e mudo a conclusão sobre o ponto aberto: subir o alignment de imagem opaca para 64 KiB é permitido para apps conformes, mas não basta para tornar o UNBIND exato no KGSL.

O motivo está no contrato de VkSparseMemoryBind:
- para buffer, resourceOffset, memoryOffset **e size** são múltiplos do alignment;
- para imagem opaca, só resourceOffset e memoryOffset precisam ser múltiplos do alignment. O size não tem essa obrigação (VUID 09492).

Contraexemplo ainda válido no sparse2:
1. imagem SPARSE_BINDING reporta alignment 64 KiB;
2. app faz BIND [0, 128 KiB); o patch cria dois ranges KGSL de 64 KiB;
3. app faz UNBIND com resourceOffset=64 KiB e size=4 KiB. Isso é compatível com o VUID de imagem;
4. KGSL child_id=0 remove o range inteiro de 64 KiB que toca [64K,68K), desmapeando 60 KiB a mais.

Portanto o sparse2 corrige bem o caso de **buffer** (porque size fica contratualmente em 64 KiB), e o split por tile parece adequado para VkSparseImageMemoryBind não opaco, mas o caminho VkSparseImageOpaqueMemoryBindInfo continua com over-unbind possível. Não recomendo o Rick testar o sparse2 como correção geral ainda.

Outro risco confirmado no kernel atual: não há limite pequeno explícito de ranges, mas kgsl_sharedmem_create_bind_op faz kvcalloc(ranges_nents, ...) com __GFP_NORETRY. Um bind de 1–2 GiB fragmentado em 64 KiB vira 16–32 mil ops num ioctl; isso pode falhar com -ENOMEM ou ter custo grande. O stress continua gate obrigatório.

Proposta para sparse3/lab:
- manter a correção de buffer separada;
- para opaque image, ou preservar/rebindar prefixo+sufixo quando um UNBIND corta um range existente, ou criar uma representação de intervalos que permita emitir operações KGSL sem perder vizinhos; não assumir que alignment restringe size;
- antes de hardware: teste mínimo com imagem opaca BIND 128 KiB -> UNBIND 4 KiB em offset 64 KiB -> verificar vizinhos, além dos casos 4097/65537 e stress 1–2 GiB;
- manter sparse1 e sparse2 como research-only, não candidato.

A falha raiz no KGSL está corroborada por um caso público A750/Bloodborne-Android: unbind parcial removia ranges inteiros e causava ErrorDeviceLost; o port contornou rebinding para uma pequena alocação em vez de null-unbind. Isso reforça o mecanismo, não valida nosso patch.

Se concordar, sugiro atualizar o survey para "sparse2: buffer fix parcial; opaque image ainda incorreto" e não enviar o ZIP sparse2 ao Rick até um sparse3 ou um teste que refute este contraexemplo.
